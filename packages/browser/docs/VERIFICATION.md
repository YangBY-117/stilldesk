## What the live checks actually did

- Initialized a real stdio MCP client, discovered 24 tools, connected through
  the native host, and asserted the absence of debugging permission/connection.
- Read main, same-origin and cross-origin documents; discovered hidden file
  inputs and closed shadow roots; checked native value setters, input/change,
  checkbox/select state, pointer events, key modifiers, DOM drag/drop, scrolling,
  literal waiting, and per-tab zoom.
- Opened a `target=_blank` link as an inactive tab; logically selected it without
  activation; refused its background screenshot rather than activating it.
- Downloaded 512 KiB + 7 generated bytes through the browser; checked the saved
  file under an explicitly allowed directory against server-generated SHA-256.
- Performed seven HTTP upload requests containing nine generated files: a
  Chinese filename, a 2 MiB + 37 byte binary, and an empty file. Server-side
  names, byte counts and SHA-256 matched across ordinary/hidden inputs,
  multiple files, both iframe origins, a closed shadow root and a non-secure
  HTTP origin.
- Rejected files outside allowed roots, multiple files for a single-file input,
  an input changed during transfer, a wrong digest, an adopted node's old UID,
  stale snapshot references and references invalidated by navigation.
- Demonstrated the trusted-event limitation with a page handler that refused
  a synthetic click. Native-dialog handling returned a typed unsupported error.
- Captured the already active viewport and created/closed background tabs.
- Queried Windows `GetForegroundWindow` and `GetCursorPos` before and after the
  action batch. The observed foreground window and pointer coordinates were
  unchanged for both browser runs. The observer only reads these APIs.

The before/after check is evidence for the tested batch; it is not a claim of
continuous monitoring of every window or every possible third-party script.
Source and action tests additionally enforce that tools do not call foreground
activation, global keyboard injection or system pointer movement. Website
scripts still execute in their normal browser environment.

## Authentication and filesystem checks

The named-pipe protocol uses a fresh server challenge and client nonce, with
separate HMAC proofs for server, client and completion. The runtime secret is
never sent to a pipe peer. A fake server test confirms that a client sends
neither its secret nor a client proof to a server that cannot authenticate.
Credentials are owner-protected. Uploads and local download verification have
independent allowed-root checks and stable-file checks. No page-facing API
accepts a path for reading an arbitrary local file.

On Windows an exact protected DACL containing only the current user's SID and
SYSTEM replaces existing directory rules in one `SetAccessControl` call. The
same operation protects an existing credential file before its contents are
read, so an explicit broad file ACE cannot survive merely because its parent
directory is private. This does not use a reset-then-grant interval. The shared
fixture starts with explicit Everyone full-control rules on both objects and
verifies that neither object retains an additional allow principal afterward.

The generated native launcher fixes `--runtime` to the setup-selected absolute
directory. A real generated Windows command launcher was tested against a
standard stdio MCP server through native length-prefixed frames and the
authenticated pipe, with a nonstandard home containing spaces. Deliberately
wrong browser-side home/runtime environment values did not change routing and
were not created. Explicit native argv takes priority over environment fallback;
duplicate, missing, relative and unsafe Windows runtime arguments are rejected.
No browser-parent environment inheritance is needed for this installation path.
DOM behavior was not repeated for this launch-only change; its affected native
launch/authentication checks were rerun.

## Browser defaults and remaining limits

CfT testing uses the official `--disable-field-trial-config` switch to remove
its embedded testing-trial overrides. No `--no-sandbox` or remote-debugging
flag was supplied. This does not assert that the separate NetworkService sandbox
is enabled: some browser versions compile that feature disabled by default.
The extension itself needs none of these testing launch arguments.

Everyday DOM workflows are covered, with explicit limits:

- DOM events do not manufacture trusted user activation. Protected site actions
  may require the user.
- Native JavaScript dialogs, OS file pickers and directory uploads are not
  automated. Files are delivered to actual file inputs instead.
- Screenshots cover only the already active visible viewport. A dedicated
  headless preview can use its own active tab without displaying a user window.
- A background new-window HTML link bypasses its custom click handler, so the
  result must be inspected. Arbitrary application-specific canvas/native UI or
  trusted-event controls are not claimed equivalent to human interaction.
- Full DevTools accessibility/network/performance/heap tooling is not provided.
- Upload and independently verified download bytes are limited to 32 MiB.
- Each runtime accepts one extension connection; simultaneous browser/profile
  multiplexing has not been implemented or claimed tested.

This is an early-access browser adapter, not a universal human-input emulator
or an assertion that every website and every agent client has been tested.
